# Phase E: assessment history and controlled retakes

Audited 2026-10-16 against the authoritative release-repo working tree. The audit/proposal below preserves the original findings. E1 grade history is now implemented as migration15, with24 actual-handler/SQLite checks and47 browser checks PASS using synthetic accounts. Retake/window work is a separate E2 increment under migration16 and is not yet accepted. See CHECKLIST.md and ACCEPTANCE_REPORT.md for the latest execution status; the proposal itself is not completion evidence.

## Current verified design and concrete gaps

- Organization membership and current teacher credential are required in `lib/server/teaching-core.ts:89`; per-class teacher assignment or active student enrollment is checked at line118. `assignmentFor` at line462 additionally restricts students to issued/closed assignments whose immutable recipient snapshot contains their user ID. New history/retake paths must reuse all three checks, including replay and export.
- Question/recipient snapshots are immutable after issue (`teaching-core.ts:1600` onward). Existing regression `tests/teaching-api.cjs:955` explicitly covers later source/group changes. Preserve these snapshots; do not reconstruct old attempts from today's question bank.
- There is one submission per assignment/student (`lib/server/teaching-schema.ts:43-48`, UNIQUE pair). A student's ungraded resubmit overwrites answers and provisional score at `teaching-core.ts:1713`; graded/published submissions lock. There is no distinct attempt identity or attempt allowance.
- `submission.grade` at `teaching-core.ts:1780` replaces grades/score/feedback, moves the result to graded, and clears publication time, including when regrading a published result. `submission.publish` at line1753 explicitly publishes again. Existing regression at `tests/teaching-api.cjs:1269` checks withdrawal, but no previous score/comment/confirmation remains in an append-only assessment history. General audit intentionally stores no scores/answers and therefore cannot reconstruct the previous grade (core line1975).
- The teacher UI disables published-grade editing (`components/teaching/assessment.tsx:596-634`), despite the server supporting regrade. The student UI disables reopening any submission (`components/teaching/student.tsx:307-342`) and always sends expectedRevision0 (line613), despite the server supporting edits before grading. These are UX/API gaps, not proof of unauthorized access.
- There is dueAt plus organization allowLateSubmissions and assignment close (core lines1666-1680), but no separate start/absolute-close window, per-assessment attempt limit, or controlled retake action. V6 section6.4 explicitly requests these. Timed/proctored exams and accommodations are broader subsequent work.
- Mastery counts distinct current assignment IDs at core lines895-947. A naive retake implemented as an unrelated new assignment would falsely inflate independent assessment counts. Group related attempts by an immutable root before offering this workflow.

## Smallest safe increment

Implement append-only grade events first, then controlled **teacher-issued practice retakes** using an explicit child assignment copied from the original issued snapshot. This avoids rebuilding the existing submissions table or changing the meaning of legacy IDs/UNIQUE pair. It is a bounded retake feature, not a complete exam engine. A retake creates one child assignment for one previously targeted, still-enrolled student. Preserve the original submission/result. Limit the family to three attempts per student initially.

Same-question retakes after answer publication are practice: previously seen answer keys cannot be made secret again. Require an explicit teacher acknowledgement and show that limitation. Do not claim a secure fresh exam. Teachers wanting different questions create a new reviewed assignment.

## Migration allocation (proposal split into two increments)

Migration15 implements the grade-event table and its two append-only guards. Migration16 is reserved for the assessment-window/retake table. Existing historical SQL is immutable; operational integrity and backup contracts must track each version separately.

1. `teaching_grade_events`: id, submission_id FK, submission_revision, kind (grade/publish/legacy_snapshot), grade_version, grades_json, score, feedback, answers_digest, actor_id FK nullable only for migrated legacy snapshots, recorded_at, reason, UNIQUE(submission_id,submission_revision,kind). Store assessment content only in this teacher/private table, never the general audit log. Grade events capture full bounded grade/feedback and a digest of the immutable submitted answers; publish events point to the grade version and do not duplicate a new grading decision. INSERT only, with UPDATE/DELETE refusal triggers. No cascading delete that silently removes history. Seed existing graded/published rows as explicitly labelled legacy snapshots; old grader/time that cannot be proved stays unknown, never invented.
2. `teaching_assessment_windows`: assignment_id PK/FK, root_assignment_id FK, parent_assignment_id FK nullable, attempt_no1..3, student_id FK nullable for base assignments, available_from, available_until nullable, revision, created_by FK, created_at. UNIQUE(root_assignment_id,student_id,attempt_no). CHECK: a base is attempt1 with root=self, parent/studentNULL; a child has parent/student and attempt2..3. Existing issued assignments default to their issued time with no hard closing window, preserving legacy late policy. New child windows have a required hard end. Add FK/lookup indexes, current schema health/backup required-table updates and capacity accounting.

Do not denormalize another unchecked organization ID into these rows: derive tenant/class ownership through the canonical submission/assignment join on every access. If organization_id is retained for an index, it is server-derived and always checked against that join. No global admin implicit cross-organization access.

## Minimal API changes

- Existing `POST /api/teaching submission.grade`: add bounded reason required for regrade after an existing grade; append grade event and update current projection in the same transaction with the existing actor/class gates, CAS, audit, and idempotency operation. Never update prior grade events. Regrading still withdraws the current result until explicit republish, preserving the established contract.
- Existing `submission.publish`: append publication event referencing the current grade version in the same transaction. Lost-ACK replay adds no second event. For students, publish history exposes only their previously published version/comment, labelled superseded/under review as appropriate; draft grades and internal regrade reasons stay teacher-only. A published answer already seen is never described as newly secret after withdrawal.
- New `GET /api/teaching/grade-history?orgId=&submissionId=&cursor=&limit=`: bounded pagination (default20, maximum50), canonical account header, current organization/class permission; teachers see bounded full grade events, students only their published events. Do not preload all history into every workspace state. Preserve same-origin/fetch-site protection. Export history is explicit and class-scoped, not a new global dump.
- Add optional availableFrom/availableUntil to **draft-only** assignment create/update. An issued assignment's question/target snapshot and window are immutable. Old omitted fields preserve legacy behavior. Window comparison is server UTC, start inclusive/end exclusive. Student payload before start contains only assignment metadata and no questions/keys/rubric; submission outside window fails even if the browser cached questions. A hard close overrides allowLateSubmissions.
- New `assignment.retake` mutation: orgId, originalAssignmentId, expectedRevision, studentId, availableFrom, availableUntil, bounded reason, sameQuestionsAcknowledged:true, requestId. Require current approved teacher plus class write scope; selected student must be an original recipient and still active/current in the class, with a submitted graded/published prior attempt. Resolve root and next attempt atomically; max3 per student, one outstanding child, fresh valid window, no arbitrary question/answer/target payload. Copy the issued root's question snapshot byte-for-byte, explicit child title/attempt metadata, one student target. Reuse teaching_operations for exactly-once child creation and replay authorization. No AI/provider calls or credit changes.
- New `assignment.retake.close` is unnecessary: the existing close action closes that child. Closing a parent does not silently reopen or close children; UI must list the explicit active retake. Credential/member/enrollment removal immediately blocks all family reads/writes/replays via existing canonical gates.
- State adds optional assessment metadata (rootAssignmentId, attemptNo, availableFrom/Until) and server-derived canSubmit/reason, no client counters. Existing submission IDs and APIs stay intact. Analytics/default gradebook choose the latest published attempt per root/student; mastery still requires three distinct roots. Explicit history can show all attempts with clear labels. Do not count one exercise retaken three times as three independent assessments.

## Minimal UI changes

- Grade editor: explicit “Chấm lại”, required reason, history drawer and publication confirmation; preserve CAS/network-error draft handling.
- Teacher assignment/submission row: “Cho làm lại” for one eligible student; time-window controls, current/maximum attempt label, same-question practice acknowledgement, explicit child close.
- Student assignment card: server-derived “Chưa mở / Có thể làm / Đã đóng / Lần làm lại2”, previous result/history and new child attempt separately. No fake past scores/names and no frontend-only allowance.
- Reports show family identity and selected latest published attempt. Existing ungraded edit support may be exposed using current submission revision; it is not counted as an additional graded attempt and remains unavailable once graded.

## Required security, rollback and migration tests

Use actual handlers and temporary SQLite, synthetic accounts/answers, no paid calls:

1. Schema14→15 and reopen preserve users, sync bytes, issued question/recipient bytes, submission IDs/current grades; migrations apply once; legacy grade history has no invented actor/time.
2. Regrade preserves old event, hides new unpublished grade, requires reason and current credential/class assignment; re-publish exposes only the correct own version. INSERT-only triggers reject mutation/deletion of history.
3. Same UUID lost ACK gives one event/child; changed payload UUID gives409; concurrent CAS gives one grade/window/retake; forced event/audit/operation insert failure rolls back projection, events and child recipients together.
4. Forged tenant/class/submission/student IDs, unassigned co-teacher, revoked credential/session, disabled account, removed/restored enrollment and stale account header. Test GET URL, POST, replay and export, not just list UI. No answer keys/history for sibling students or unrelated organizations.
5. Before-start and at/end-boundary GET and submit checks, including cached questions, timezone strings normalized to UTC, invalid/reversed/oversize windows, closed child and archived class. Forged clock/attempt number/payload cannot bypass the server.
6. Retake copies exact original snapshot after today's question/group/source edits, targets only the eligible original student, retains all original answer/grade rows, never grants an unrelated student. Max3 and one outstanding child enforced in the transaction; failed creation consumes no attempt.
7. Prior published answer visibility is accurately labelled practice; unpublished answer keys/internal reasons never appear in student JSON/history/export. Three attempts of one root do not satisfy the three-assessment mastery threshold.
8. Capacity limits cover events/child snapshots and paginated history; denied quota actions write no audit/idempotency residue. Export formula and tenant protections remain intact.

## Receipt/credit security rereview (Phase B code)

No additional authorization/atomicity defect was found in the scoped rereview: owner headers and canonical session checks precede provider dispatch; normalized UUID receipts precede paid daily/concurrency quota; onSettled validates current actor, lease token, abort and source revision within the ledger transaction. Receipt-write faults roll back ledger/vector/tutor writes; guarded failure fencing and idempotent refunds prevent a late completion from reviving a failed intent. The final focused run passed88 checks (27 paid-RAG +30 API safety +10 RAG lifecycle +21 previous RAG regression), with fake provider transport and no live call claim.

Limits remain explicit: the generic authenticated RAG HTTP abuse throttle counts each retry, whereas paid AI quota/reservation/provider count does not; receipts cache metadata, not audio/answers; completed lost output cannot be silently regenerated. Abandoned recovery is access-driven, and the exact-once protection depends on the SQLite ledger surviving. An ephemeral competition-host database reset cannot retain old tombstones. This is not a global provider-side exactly-once guarantee.
